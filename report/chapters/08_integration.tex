\chapter{Integrating Flask and the Cloud API}\label{ch:integration}

\textbf{How it works.} The web app has two interchangeable back-ends behind one interface
(\file{app/predictors.py}): \texttt{LocalPredictor} wraps the in-process \texttt{Predictor};
\texttt{RemotePredictor} sends the validated image bytes as multipart form data to
\texttt{MODEL\_API\_URL/v1/predict} with the \texttt{X-API-Key} header over HTTPS, through one
re-used \texttt{requests.Session} (connection pooling) with a 30\,s timeout. Switching is one
environment variable, \texttt{INFERENCE\_MODE=remote}; routes, templates and the database code are
unchanged. In remote mode the web image can be built without TensorFlow
(\texttt{WITH\_TF=false}), because the model lives only in the cloud.

The flow per upload: the browser posts to \texttt{/predict} $\rightarrow$ the web app validates
the file locally (wrong types never leave my machine) $\rightarrow$ calls the API $\rightarrow$
stores the decision, the model version reported by the API, \texttt{inference\_mode = remote} and
the round-trip latency in the database $\rightarrow$ shows the result page. For this test the web
app ran directly on my Windows laptop (\file{scripts/run_local.ps1}: virtual environment,
\texttt{FLASK\_DEBUG=0}, history in a local SQLite file through the same SQLAlchemy code); in the
Compose stack the same code writes to PostgreSQL (\cref{ch:db}). If the API is unreachable
or answers with an error, the user gets a friendly 503 page and the attempt is still recorded with
\texttt{status = error}.

\textbf{Multi-input test.} I uploaded six held-out test images from my laptop through the UI
(three AI-generated, three real). All six were answered by the cloud model (version 8) and logged
with \texttt{mode = remote}. All three real photos were classified correctly with high
confidence ($p(\text{AI})$ 0.004, 0.005 and 0.32), and one of the three AI images was caught
($p(\text{AI}) = 0.69$, just above the 0.62 threshold). The other two AI images (0.28 and 0.23) were
called real, so 4 of 6 were correct. This matches the operating point I chose on purpose in
\cref{sec:2-5}: the threshold favours precision (no real photo was accused) at the cost of
recall on the AI class (test recall 0.66), and the two misses are photorealistic renders, the
same error type as in \cref{sec:2-6}. The API logs show about 70\,ms of model time per image on the
VM, while the round trip seen by the web app (Lahore $\rightarrow$ Central India over HTTPS) was
197--416\,ms. The earlier rejected uploads (415, 422) never reached the API, because validation
happens locally first.
